# Production operations readiness

This is a preparation checklist, not a deployment authorization. The public
Render blueprint intentionally uses `MARKET_PROVIDER=csv` and `csv-demo` data.
Keep it that way until the upstream provider confirms written storage and
display rights. Vnstock Community is for local experimentation only. No
production domain or data rights are currently confirmed.

## Before provisioning a public environment

- Confirm the intended Render region, service plans, database plan, expected
  monthly cost, and who owns the account. Review current provider pricing in
  the dashboard before creating resources.
- Configure `CORS_ORIGINS` to the exact HTTPS frontend origin(s), with no
  wildcard. Keep `JWT_SECRET` generated by the platform or set a unique,
  random secret; never reuse a local value. Keep `OPENROUTER_API_KEY` optional
  and scoped to the backend web service only.
- Keep `MARKET_PROVIDER=csv`, `RUN_SNAPSHOT_JOBS=false` on web, and do not add
  `VNSTOCK_API_KEY` to either public service. Keep provider and AI secrets out
  of frontend build variables, source control, issue text, and logs.
- Confirm that database backups / point-in-time recovery are enabled for the
  selected PostgreSQL plan and record retention and recovery-point limits.
  The current blueprint does not specify a backup policy.
- Apply migrations and smoke-check `/health`, `/ready`,
  `/api/v1/market/overview`, and `/api/v1/stocks?limit=10`. Verify the response
  provenance remains `csv-demo` / `synthetic-demo`.

## Backups and restore drill

PostgreSQL is the durable source for symbols, news, market snapshots, bars,
event studies, accounts, and job history. Treat Redis as disposable cache. The
Compose `postgres_data` volume is not a backup; losing the Docker volume loses
the local database.

For a hosted environment, use the managed PostgreSQL backup facility selected
in the dashboard. Record the backup schedule, retention window, and a named
operator. Before a release that changes schema, confirm a recent restorable
backup exists. At least once before launch, restore a backup into a separate
temporary database, run `alembic upgrade head`, and verify core tables and a
sample API read. Record the drill date and elapsed recovery time in the team
runbook. Never test restore by overwriting the live database.

For local Compose, create an explicit dump before destructive maintenance:

```powershell
docker compose exec -T db pg_dump -U finsight -d finsight -Fc > finsight-backup.dump
```

Store that dump outside Git and verify it is non-empty. A restore requires a
separate empty database and `pg_restore`; do not restore over the only copy.
The Compose database credentials are development defaults and must never be
reused for a hosted database.

## Monitoring and incident signals

- Configure the hosting platform's HTTP health check to `/ready`. It verifies
  database connectivity and Redis when configured; it does not verify worker
  progress, provider freshness, frontend availability, or data quality.
- Check platform logs for repeated worker restarts, migration failures,
  database connection errors, and exceptions. Logs are not a durable audit
  store; do not log credentials, authorization headers, or provider payloads
  containing account identifiers.
- Track `/api/v1/market/data-status` for the active source, latest bar date,
  stale/no-data state, and last provider job summary. CSV demo data is expected
  to remain explicitly synthetic. A future authorized real provider needs
  freshness and failed-job alerts before it is enabled.
- Review database storage/connections and Redis memory in the hosting dashboard.
  Establish alert thresholds from the selected plan's limits before launch.
- After deploy, exercise login/session flows only with test accounts, confirm
  browser requests reach the configured domain, and verify CORS rejects an
  unrelated origin.

## Recovery notes

If `/ready` returns 503, inspect its `database` and `redis` fields, then check
managed service status and connection configuration. If the web service is
healthy but market data is stale, inspect worker logs and
`provider_job_runs`; do not switch providers silently. If a migration fails,
stop rollout, preserve the database, inspect the migration error, and recover
using the managed backup procedure. Do not delete or recreate the database as
a troubleshooting shortcut.
